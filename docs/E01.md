# E01 — evaluate generated answers, not the reference answer

## The defect

Before this change, `evaluator.py` built its RAGAS input like this:

```python
data = {
    "question": [case.question],
    "answer": [case.reference_answer],   # reference stands in for generated
    "contexts": [case.retrieved_contexts],
}
```

The answer being scored was the human-authored ground truth. A perfect score was
therefore guaranteed regardless of what any application produced. A green run
proved the plumbing worked and said nothing about quality — the most dangerous
kind of test, because it looks like evidence.

E02 mitigated this by disabling real mode entirely. That was correct as a stopgap
and wrong as a destination: it left the harness unable to measure anything.

## The contract now

| Field | Role |
|---|---|
| `question` | input |
| `retrieved_contexts` | what the application was given |
| `reference_answer` | ground truth — **never scored** |
| `generated_answer` | what the application produced — **what gets scored** |

Rules enforced in code:

1. `GoldenCase.generated_answer` is a separate field from `reference_answer`.
2. Real scoring raises `MissingGeneratedAnswer` when it is empty. There is no
   fallback to the reference, and no silent skip.
3. `Evaluator.ragas_payload()` — the single place the RAGAS input is built — puts
   `generated_answer` in `answer` and never includes `reference_answer`. It is a
   separate function so the contract can be asserted without the datasets/ragas
   dependency chain.
4. Real mode still refuses when `OPENAI_API_KEY` is absent, before loading an SDK.
5. A case the application could not answer is scored as a failure, not skipped.

## Why the payload is separated from the transport

`ragas_payload()` exists because the important property — *which text reaches the
judge* — should be testable in the offline CI environment, which deliberately
contains only `pytest`. Coupling that assertion to installing `datasets`, `dill`
and `pandas` would have meant the contract was only checked where the heavy stack
happens to be installed. The bug was precisely a mismatch between fields, so the
test targets the fields.

## Verification

**Offline (runs in CI, no provider key):** 23 tests. The ones that matter:

- the scorer receives the generated answer and not the reference;
- scoring refuses a missing and a whitespace-only generated answer;
- the RAGAS payload contains the generated answer and the reference string
  appears nowhere in it;
- a wrong generated answer **fails the gate while a correct reference is
  present**, and a correct generated answer passes;
- a real run with no generated answers cannot pass even when the injected scorer
  would return a perfect score;
- mock mode cannot satisfy a live-quality requirement;
- real mode without a credential refuses before loading RAGAS.

The suite runs under a no-network pytest plugin, so an accidental outbound call
would fail rather than silently succeed.

**Live (not in CI, requires a key):** see `evidence/E01.md`. The key result is
that the two halves of the acceptance criterion were demonstrated against a real
judge:

- correct generated answers → `live_pass` (faithfulness 1.000, relevancy 0.910);
- deliberately wrong answers, with correct references present →
  `live_fail` (faithfulness 0.000, relevancy 0.000).

## Environment findings (worth knowing before repeating this)

1. **Python 3.14 breaks the live path.** `datasets`/`dill` serialisation fails
   with `TypeError: Pickler._batch_setitems() takes 2 positional arguments but 3
   were given`. Real mode requires a supported interpreter; the project targets
   3.11 and the live run was performed on CPython 3.11.9.
2. **Unbounded `langchain` breaks `import ragas`.** `ragas` 0.2.x imports
   `langchain_community.chat_models.vertexai`, which moved out of
   langchain-community in 1.x. `ragas>=0.2` with `langchain>=0.2` resolves to 1.x
   and fails at import. Pin `langchain>=0.3,<0.4` (and the matching community and
   openai packages) when running live.

Neither is a code defect, and both are recorded here so the next person does not
spend an hour rediscovering them.

## Limits

- Three cases is a smoke test of the harness, not a benchmark of anything. Do not
  quote the numbers as a quality result for any system.
- The thresholds (0.90 / 0.85) are configuration, not validated acceptance
  criteria. Calibrating them against known-bad cases is E04.
- Nothing in CI runs a live evaluation, so a green workflow still does not mean a
  deployment was quality-gated. Wiring that is R01/O02 territory.
- RAGAS's judge is itself a model; its verdicts are not ground truth. A
  human-reviewed sample and disagreement check remain unbuilt.
